# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Static website for Trackbolt (Colombian heavy-machinery fastener distributor), replacing their
Shopify site at trackbolt.co. The product catalog is **generated by a Python script** from the
ERP's stock-report spreadsheet, then consumed by an Astro build. All content, code identifiers and
comments are in **Spanish** — keep it that way.

The active project lives in `trackbolt-web/`. Files at the repo root (`transform_catalogo.py`,
`catalogo_rex.html`, `correo_catalogo_rex.html`, `existencias_*.xlsx`) are the **superseded one-off
script** and its output; don't edit them — `trackbolt-web/scripts/` replaced them.

(the Makefile refers to it as `../.venv`).

../.venv/bin/python -m pytest scripts/tests/test_catalogo.py::test_grado -q

## Architecture: a two-stage pipeline

**Stage 1 — Python** (`scripts/build_catalogo.py`) reads `data/inventario … .xlsx` and emits JSON.
**Stage 2 — Astro** imports that JSON at build time and emits static HTML.

Astro never touches the spreadsheet. If a page shows stale data, the fix is almost always to re-run
`make catalogo`, not to change a template.

The ERP gives one flat sheet: `Bodega | Tipo | Linea | Sublinea | Producto | Unidad | Cantidad |
Total | Promedio`, where `Producto` packs `codigo | linea | descripcion` and everything technical
(diameter, length, pitch, grade, finish, OEM part number) is buried in free text inside
`descripcion`. Stage 1 exists to turn that into structured, filterable fields.

### Generator modules (`scripts/lib/`)

| Module | Responsibility |
|---|---|
| `lector_excel.py` | openpyxl read; **validates the header** and aborts loudly if the ERP reorders columns. `partir_producto` uses `split("|", 2)` — one row's description contains an extra `|`. |
| `normalizar.py` | Text cleanup, known ERP typos, and `base_comercial()` which turns an ERP sublinea into the product's base name by stripping words already shown as specs. |
| `especificaciones.py` | The parser. Extracts diameter/length/pitch/grade/finish/head/thread/OEM from free text. |
| `taxonomia.py` | `LINEAS` metadata + `clasificar()` mapping ERP triples to the 11 public product lines. |
| `precios.py` | Price tiers and commercial rounding. |
| `salidas.py` | JSON writing. |

### Outputs, and the public/internal split

| File | Contents | Shipped to browsers |
|---|---|---|
| `data/generado/productos.json` | Full public catalog — **no cost, no quantity** | no (build-time only) |
| `data/generado/productos-interno.json` | + `costo`, `cantidad`, `valor_inventario`, 4 price tiers | no (build-time only) |
| `data/generado/lineas.json` | Lines, groups, facet values with counts | no (build-time only) |
| `data/generado/reporte.json` | Timestamp, totals, data incidents | no (build-time only) |
| `public/datos/buscador.json` | Search/filter index | **yes** |
| `public/datos/interno.json` | Internal view index | **yes** |

**Invariant: `productos.json` and `buscador.json` must never carry `costo` or `cantidad`.** The
customer-facing decision is "availability status, no numbers"; the protection is that the data
simply isn't in the file the browser downloads. If you add a field to `construir()`, put it in
`comun` only if the public site may show it — otherwise add it to the `internos` dict alone.

### Parser design rules (`especificaciones.py`)

- **Prefer `None` over a wrong value.** Every field may be null and templates skip nulls.
- Metric measurements come from `_MM_CANDIDATOS`, an **ordered** list of `(regex, builder)` pairs,
  most specific first. Each candidate's result passes `_valida_mm()` (diameter 2–64 mm, pitch
  0.3–6.5, length 4–600 and never under 35 % of the diameter); rejects fall through to the next
  candidate. Inserting a candidate in the wrong position silently changes thousands of rows —
  after any edit here, run `make test` and diff the "sin medida reconocida" count.
- Before measuring, `extraer()` strips noise that looks like a measurement: OEM part numbers,
  `F-436`, `CL10.9`, `G8`, `ESTRIA 23`, nut styles `2H/6H`, `304/316`, gauges `Nº10`. Inch
  fractions only accept denominators 2/4/8/16/32/64, so vehicle models like `250/350` and
  `416/420` are not read as sizes.
- `roscado=False` (arandelas, pines) renders a diameter as `20 mm` instead of `M20`, because there
  is no thread to designate.
- OEM part numbers (`6Y0846` Caterpillar-style, `20Y3211210` Komatsu-style) drive search by
  manufacturer part number — a deliberate feature, not incidental.

### Taxonomy

`clasificar(tipo, linea, sublinea, descripcion)` is an **ordered rule list** and the order carries
meaning: nuts are matched before flange and before rodaje, so `TUERCA FLANGE` and `TUERCA ZAPATA`
stay in `tuercas`. Anything unmatched falls into `otros` and is reported on stdout and in
`reporte.json` — a new ERP line never disappears silently.

Adding a product line means editing both `LINEAS` (metadata, ordering, description) and
`clasificar()`, plus adding an SVG case in `src/components/IconoLinea.astro`.

## Astro side

- `src/components/Catalogo.astro` holds **all** the site's client JavaScript (~4 KB). It fetches
  `/datos/buscador.json` and filters in the browser; no framework, no dependencies. The same
  component serves `/catalogo/` and each `/lineas/[linea]/` page via the `lineaFija` prop.
- `buscador.json` uses **single-letter keys** to stay small (`c` code, `n` name, `l` line, `g`
  group, `r` grade, `d` diameter, `a` finish, `h` head, `t` thread, `s` system, `v` vehicle,
  `k` part number, `e` stock state, `q` REX flag, `x`/`y` sort keys). Renaming a key requires
  changing `construir_buscador()` in Python **and** the filter loop in `Catalogo.astro` together.
- Filter state is mirrored into the URL query string, so `/catalogo/?r=Clase+10.9` works as a
  shareable link — `src/data/colecciones.ts` relies on this for the cross-cutting collections.
- `src/data/indice.ts` builds the related-products map **once per build**; product pages import it
  rather than rebuilding a 2.790-entry map in each of 2.790 frontmatters.
- `src/data/sitio.ts` is the single place for company data and page copy (phones, address,
  mission, FAQ). Prefer editing it over hardcoding text in templates.
- Price multipliers are duplicated in `scripts/lib/precios.py` and `src/data/precios.ts` (the TS
  copy only feeds the informational line on `/interno/`). **Keep them in sync.**
- `/interno/` shows costs, exact quantities and all four price tiers. It is `noindex` and excluded
  from the sitemap (`astro.config.mjs` sitemap `filter`), but **intentionally unprotected** — the
  client chose that for this proof of concept. Don't add auth without asking; don't remove the
  warning banner or the `noindex` either.
- Two env vars change the build: `TRACKBOLT_URL` overrides `site` (canonicals + sitemap), and
  `TRACKBOLT_DEMO=1` flips `ES_DEMO` in `src/data/demo.ts`, which mounts `BannerDemo.astro` and
  forces `noindex` sitewide. Unset, the build is byte-identical to production.

## AWS demo (`trackbolt-web/infra/`)

Private S3 bucket + CloudFront with Origin Access Control, on the default `*.cloudfront.net`
certificate. Terraform state is **local** and gitignored, in the `default` workspace.

- Everything lives in AWS account **006392690655**, `us-east-1`. The provider pins
  `allowed_account_ids = [var.cuenta_aws]` and `desplegar.sh` compares `sts get-caller-identity`
  against the `cuenta` output, so a run with another account's credentials aborts up front. This is
  deliberate: the bucket name is globally unique, so foreign credentials get a 403 rather than a
  "not found", CloudFront finds nothing, and Terraform proposes recreating the whole stack in the
  wrong account. Keep the account id in `variables.tf` — `*.tfvars` is gitignored.
- `var.entorno` is `demo` or `produccion`. It drives `force_destroy` on the bucket, the
  `TRACKBOLT_DEMO=1` banner, and whether `desplegar.sh` overwrites `robots.txt` with `Disallow: /`.

- `funciones/reescribir-rutas.js` is load-bearing: Astro emits directory URLs and the S3 REST
  origin has no per-folder index document, so without this CloudFront Function every route except
  `/` returns 403. Its "last segment has no dot ⇒ it's a directory" heuristic is safe only because
  ERP product codes are numeric.
- `desplegar.sh` syncs in **two passes** with different `Cache-Control` (`/_astro/` immutable for a
  year, everything else 60 s). Each pass carries its own `--delete` scoped by the same filters —
  keep those filters mirrored or one pass will delete the other's files.
- The script rewrites `dist/robots.txt` to `Disallow: /` after building, because `public/robots.txt`
  advertises the production sitemap.
- The demo publishes the **whole** site, `/interno/` included, on a public URL. That was the
  client's call; see the README section before changing it. `publicar_interno = false` is the
  switch that excludes it from both sync passes — the default stays `true`.

## Verifying a change

`make test` covers the parser, taxonomy and pricing with real strings lifted from the spreadsheet —
add fixtures from the actual data rather than invented ones.

For catalog changes, the useful end-to-end check is that browser-side filtering reproduces the
counts Python computed: every facet value's `total` in `lineas.json` must equal the number of rows
in `buscador.json` matching that value, and each line's `total` must equal its row count. A short
Node script that replays the filter logic against the two JSON files catches key mismatches that
neither pytest nor the Astro build will.
